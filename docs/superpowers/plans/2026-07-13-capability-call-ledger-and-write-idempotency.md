# MindAtlas Capability Call Ledger and Write Idempotency Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use `superpowers:executing-plans` task-by-task. Start only after full Plans 01–07 are merged and Plan 07 proves exact durable pause/resume. The hard gate includes Plan 06 allowed-source + `state_revision` stop/result convergence and Plan 07 idempotency-before-consumed-token resolution, public terminal `resolutionRequestId`, versioned budget suspension, and parent-budget/resume-Checkpoint lineage. `ASSISTANT_MAIN_AGENT_WRITE_MODE=golden` must remain impossible until those PostgreSQL/fixed-vector gates pass.

**Goal:** Give every durable Capability invocation a persistent identity, attempt history, authorization/approval evidence, idempotency boundary, output reference, and reconciliation state, then enable exactly one approved local-write golden path without duplicate writes across retries, process loss, reconnects, or competing workers.

**Architecture:** Insert a CapabilityCall ledger between the Provider/Workflow planner and the shared Capability Gateway. All logical calls are proposed durably before dispatch. A versioned Plan 05 policy delta derives one exact golden `write_local` grant from independent server policy before approval; approval is a call-owned obligation and never a grant source. Read/compute calls reuse the same record after recovery; local writes combine the business mutation and ledger success in one database transaction; external writes use declared provider idempotency/reconciliation contracts or stop as `unknown`. Plan 08 extends Plan 07 with a discriminated call-owned Interrupt profile while preserving Plan 07 as the only waiting-Run commit path.

**Prerequisites:** Plans 01–07, including source-aware policy, frozen Manifest versions, durable budget/obligation revisions, worker lease/CAS, durable Artifacts, and nonblocking interrupts.

At plan-authoring time the repository facts that Task 0 must reconfirm are:

- Plan 05 policy contract v1 has an explicit hard release gate and independently derived grant prefix limited to `none | compute | read`; a write cannot reach approval merely because its descriptor is `write_local`.
- Plan 06 ordinary results require `status=running` and cannot commit while the Run is `cancelling`; its cancellation finalizer does not yet settle a ledger call whose external effect already started.
- Plan 07 Interrupt v1 is Workflow-node-shaped: `workflow_frame_id`, `node_id`, and `node_visit_id` are required, while `capability_call_id` is reserved/null until this plan.
- `backend/app/entry/service.py::EntryService.create()` validates, flushes `Entry`, inserts `EntryIndexOutbox`, calls `commit()`, and refreshes. `backend/app/assistant/tools/entry_tools.py::create_entry()` calls that committing method directly.
- The current `smart_capture` asset has two human nodes, create/update branches, and an unconditional post-write `smart_capture_relation_followup`; that child can create relations. The complete asset is not the Plan 08 golden Workflow.

Grant and admission rules are locked:

1. 7. All other local writes—including update, delete, merge, relation creation, current full `smart_capture`, dynamic Workflow branches, and a different `create_entry` binding/version—remain absent from the golden Manifest or hard-denied independently by both policy and Gateway.

## Locked CapabilityCall State Machine

~~~text
proposed
  -> denied | awaiting_approval | authorized | cancelled

awaiting_approval
  -> authorized | rejected | cancelled | expired

authorized
  -> executing | cancelled

executing
  -> succeeded | failed | cancelled | unknown

unknown
  -> needs_reconciliation

needs_reconciliation
  -> succeeded | failed | compensated
  -> authorized (only when the mode matrix below permits an explicitly approved same-key retry)
~~~

Rules:

- Terminal success/failure/rejection/cancellation never returns to ordinary automatic execution.
- `executing` means a dispatch attempt owns the call, not necessarily that the effect started; the mode-specific `side_effect_started_at` rule is the irreversible boundary.
- `executing -> cancelled` is legal only while `side_effect_started_at` is null. After an effect may have started, cancellation records intent but the outcome must become proven success/failure or reconciliation, never a false cancelled result.
- A `local_transactional` call never commits a standalone pre-mutation `side_effect_started_at`. Its Entry/outbox mutation, inline result, Attempt `committed`, call `succeeded`, timestamp, Checkpoint/events, and Run revision commit in one PostgreSQL transaction. Therefore no durable local state may exist as `executing + side_effect_started_at != null`.
- External modes commit `side_effect_started_at` before network send. Once committed, API stop may request cancellation but cannot make the call or Run falsely terminal until the call-aware settlement rules below run.
- A worker may recover a stale `executing` read/compute call according to its descriptor. A write follows the mode-specific rules below.
- `unknown` is a transient classification step committed immediately after an uncertain response; automatic workers then move the Run/call to `needs_reconciliation` and stop.
- The Run cannot complete while any call-owned approval or reconciliation obligation is pending.
- State transitions, attempts, budget/obligation revisions, Checkpoints, and events are committed through Run CAS.

### Run and call cancellation join

Plan 08 does not weaken Plan 06's rule that ordinary Provider/Capability results cannot commit from `cancelling`. It adds one narrow `CapabilityCallSettlementRepository` transition family for calls whose effect boundary already committed. This path may persist an already-received trusted result/Artifact, finish the already-started budget reservation, apply result-owned obligations, and append its exact Tool pairing/Checkpoint/event, or classify an existing Attempt; it may not invoke a Provider, Gateway, adapter, fallback, compensation, or new business mutation.

| Call/effect state when stop wins | Required behavior |
|---|---|
| `proposed`, `awaiting_approval`, or `authorized` | cancel/reject the unstarted call and obligation, seal pairing, then allow normal Run cancellation |
| `executing`, `side_effect_started_at=NULL` | mark Attempt abandoned/call cancelled; no effect may start after the stop revision |
| `local_transactional` atomic commit racing stop | both transactions require the same Run/call revision and lock order; stop-first makes the business transaction roll back completely, atomic-success-first leaves one `succeeded` call/Entry/outbox/result |
| external `executing`, effect started, trusted response already captured | special settlement may commit call `succeeded` or `failed` from Run `cancelling`; the call result remains honest even though later Run cancellation sealing may finish as cancelled |
| external `executing`, effect started, outcome not proven | special settlement commits call `unknown -> needs_reconciliation`, creates/retains the reconciliation obligation, and moves Run `cancelling -> needs_reconciliation`; it must not finalize Run `cancelled` |
| all started calls have proven terminal outcomes and no reconciliation remains | cancellation sealer pairs/cancels the remaining unstarted suffix and may commit Run `cancelling -> cancelled` without rewriting a succeeded call |

Plan 08 therefore versions the Plan 06 transition table with exactly one new Run edge: `cancelling -> needs_reconciliation` when an already-started call cannot be proven. A `cancelling` recovery takeover first classifies durable Attempt evidence without external I/O. It cannot finalize `cancelled` while any call has `side_effect_started_at != null` and a nonterminal/unproven status. PostgreSQL two-Session tests must prove stop versus local atomic success, stop versus external pre-send boundary, late response settlement, unknown classification, duplicate settlement, and cancellation finalizer refusal.

### Reconciliation retry matrix

`retry_same_key` is not a generic exit from reconciliation:

| Execution mode | `retry_same_key` from reconciliation |
|---|---|
| `pure_replayable` or `read_replayable` | not a reconciliation action; normal recovery creates a new Attempt under the same logical call |
| `local_transactional` | forbidden; query the atomic ledger/business state—committed means `succeeded`, absent means the original unstarted/rolled-back call may follow normal recovery |
| `external_idempotent` | allowed only by explicit operator decision, identical frozen request, identical server key, bounded remaining attempts/deadline, and provider contract evidence |
| `external_reconcilable` | blind retry forbidden; perform status lookup first, then mark proven success/failure or permit same-key resubmit only if the provider contract proves `not_accepted` is authoritative |
| `non_retriable` or `unsupported` | forbidden |

No reconciliation action changes target, input, owner, approval, authorization, or key. A local Entry success is never dispatched again merely because the worker missed the commit response.

|---|---|

## Locked Execution Modes

Extend the Capability descriptor/classification registry with one explicit mode:

| Mode | Eligible targets | Recovery rule |
|---|---|---|
| `pure_replayable` | `none`, deterministic `compute` | retry same logical call within budget |
| `read_replayable` | bounded reads | retry same logical call; result may be refreshed, attempt remains audited |
| `local_transactional` | local DB mutation supporting shared UoW | mutation + success + result/event pointers commit atomically |
| `external_idempotent` | provider documents an idempotency key contract | retry only with identical server key and bounded policy |
| `external_reconcilable` | provider supports status lookup by stable request ID/key | query status before any retry |
| `non_retriable` | mutation without provable idempotency/reconciliation | uncertainty becomes `needs_reconciliation`; never auto-retry |
| `unsupported` | unknown/dynamic/unclassified | deny |

The side-effect class and execution mode are separate. A remote read can still be non-replayable; a local write can be transactionally safe. Missing classification defaults to `unsupported`, never inferred from Tool name or model text.

For enforced Runs, a recovered read/compute may append another Attempt under the same logical call; this is expected audit history, not another logical call or another started-budget charge. Proposal/claim/result transactions are short, and no ledger/Run row lock or SQLAlchemy Session remains open across Provider, Gateway adapter, network, MinIO, or long compute execution.

### Server idempotency key

~~~text
HMAC(server_secret,
     runtime_contract_version || run_id || logical_call_key ||
     frozen_target_digest || canonical_input_digest)
~~~

- The model cannot supply or override it.
- Recovery of the same logical call gets the same key.
- A new intentional logical call gets a different key even with identical arguments.
- Adapters pass it only to targets whose declared API supports it.
- Logs/events expose only a short non-secret diagnostic fingerprint.

## Dispatch Protocol

### 1. Propose and authorize

Before adapter execution:

1. normalize Provider/Workflow call identity and validate input;
2. resolve exact exposure/owner/descriptor from the frozen Manifest;
3. create-or-verify `proposed` ledger row and input Artifact;
4. evaluate the Run's frozen Plan 05 v1/v2 policy and independently derived grant before inspecting approval state;
5. deny a write unless the exact v2 golden release/entrypoint/Profile/owner/cohort sources produce a `write_local` grant and immutable `authorization_digest` without copying descriptor behavior;
6. reserve budget; read/compute transitions to `authorized`, while the exact golden write transitions to `awaiting_approval` and creates one call-owned obligation/pause proposal;
7. issue no executable Gateway authorization evidence for `awaiting_approval`;
8. let Plan 03 build the waiting continuation, then persist call, Interrupt, budget suspension, obligations, Checkpoint, waiting Run state, and events through the one extended Plan 07 pause CAS.

Possession of a Provider Tool Call does not authorize it. Replayed call IDs with changed arguments, owner, target, version, or descriptor digest fail as corruption/reconciliation.

### 2. Approval binding

The approval card must display safe, server-derived summaries of:

- action and affected object/type;
- exact normalized fields that will be committed, with secret/private redaction rules;
- side-effect class and whether external;
- target/version and owner display labels;
- whether the action is retryable/reconcilable.

Approval binds `call_id + logical_call_key + owner_digest + binding_contract_digest + input_digest + target_version/target_digest + descriptor_digest + authorization_digest + principal_digest + request_revision`. Any changed field invalidates the pending call/Interrupt; it is never silently rebound. Approval never grants the Skill or Run a reusable write permission and never changes the independent grant/authorization digest.

### 2.1 Call-owned Plan 07 pause profile

The Plan 08 golden path uses one call-owned approval generated by `LedgerDispatcher`; it does not retain a Workflow `human_in_loop` node before `create_entry` and does not ask twice.

1. The dispatcher derives deterministic call/Interrupt/root-continuation identities, moves only the proposed call state into the staged `CapabilityCallPauseProposalV1`, and returns the ordinary waiting Capability result expected by Plan 03. It writes no Interrupt/Run status itself.
2. Plan 03 persists the same outer waiting call/sibling continuation shape as Plan 07. The outer worker consumes exactly one matching proposal after lineage/protocol validation.
3. One extended Plan 07 Section 11.1 CAS owns all durable visibility: call `awaiting_approval`, exact obligation, call-owned Interrupt, approval evidence Artifact, Plan 07 `BudgetSuspensionStateV1`, Provider continuation, Checkpoint, `running -> waiting_approval`, and events.
4. Resolve reuses Plan 07's Run-first lock, idempotency lookup before consumed-token/pending validation, terminal public `resolutionRequestId`, budget child, and `interrupt_resume` Checkpoint. In the same transaction, approved changes the exact call to `authorized`; rejected/expired/cancelled terminalizes it with a typed result and never claims an Attempt.
5. A successful approval resume still closes the original Plan 03 waiting call only after the authorized call reaches a terminal Capability result. A reject/cancel/expire result may close it immediately according to the frozen call contract. No second waiting resolution is introduced.
6. Whole-Run stop while waiting uses the same aggregate transaction to terminalize the pending Interrupt/call, release the unstarted reservation, close the approval obligation, and apply Plan 03 cancellation sealing; it never creates an Attempt or active resume budget.
7. Every aggregate path locks Run first. When existing rows participate, lock Interrupt before Call; call-only paths lock Call after Run. The Run lock serializes same-Run mutations, and no code may acquire these rows in reverse order.
8. Missing/mismatched proposal, call, binding digest, suspension lineage, continuation, or pending-package ownership is fatal before Run waiting/queueing. A crash before the one CAS leaves neither durable layer; replay converges on the same logical call/Interrupt.

### 3. Dispatch

- Verify lease, cancellation, exact terminal call approval, unchanged independent grant/authorization digest, budgets, obligations, frozen versions, and call state immediately before dispatch.
- Append/claim an Attempt through CAS.
- For writes, mark the side-effect boundary using the mode-specific protocol before or atomically with the mutation.
- Issue fresh Gateway evidence only now. For an approval-gated write it carries the frozen pre-approval grant/decision plus linked approval evidence; approval is not an evidence issuer or grant source.
- Pass the immutable input and server idempotency context to the adapter.
- Normalize output into an Artifact; update the call and outer Checkpoint/events through CAS.
- Charge a dispatched attempt even if it later fails or becomes uncertain.

### 4. Multiple sibling calls

- Create all sibling ledger rows and reserve allowable budget before any sibling starts.
- Read/compute siblings may run concurrently only under Plan 02/05 `parallel_safe` limits.
- Write/external siblings execute sequentially in Provider order in the first release.
- At most one pending interrupt per Run; later write siblings remain `proposed` until earlier siblings resolve.
- The next Provider request occurs only after every Tool Call in that assistant message has one persisted matching Tool Result.
- Rejection/cancellation produces a typed Tool Result for that call; it does not erase completed siblings.
- Once any sibling crosses `side_effect_started_at`, no alternate target/fallback execution is permitted for that logical call.

## Local Transactional Write Contract

The golden `create_entry` path must stop creating its own opaque database lifecycle. Introduce an adapter-facing Unit of Work so one SQLAlchemy transaction can:

1. lock/verify the authorized call and active lease/revision;
2. write the Entry and any tags that belong to this atomic operation;
3. persist a stable business result reference;
4. mark the Attempt/call `committed`/`succeeded`;
5. append result Artifact, budget/obligation changes, Checkpoint, and events;
6. commit once.

Crash before commit leaves neither business mutation nor success. Crash after commit leaves both. Recovery sees `succeeded` and returns the stored result without calling `EntryService.create` again.

Requirements:

- Extract the exact no-commit core `EntryService.create_in_uow(request, *, source_capability_call_id) -> Entry`. It uses the caller-owned Session already held by `CapabilityUnitOfWork`, performs existing type/tag validation, Entry/tag/outbox adds and flushes, and never calls `commit`, `rollback`, `close`, `begin`, nested Session construction, or post-commit external work.
- Keep `EntryService.create(request)` as the compatibility wrapper for HTTP/Legacy callers: call the same core with `source_capability_call_id=None`, commit once, refresh, and preserve the current response/error behavior.
- The `local_transactional` Gateway adapter must call only the no-commit core. It must not call the existing decorated `create_entry` Tool wrapper or `EntryService.create()`. Add an import/call-graph architecture test plus a runtime spy that raises if `Session.commit()` occurs below the ledger-owned UoW.
- Keep `_build_entry_request`/tag normalization on the caller-owned UoW Session so newly created tags roll back with the Entry/call. Do not route golden tag creation through `TagService.create()`, which owns a commit.
- Add `source_capability_call_id` to the created Entry, unique when non-null. Do not overload a user-visible field.
- Store the small normalized `create_entry` result in an inline database Artifact inside this transaction. Do not make the golden path's atomic success depend on a separate MinIO write.
- Insert the existing `EntryIndexOutbox` row in the same transaction. Its consumer must be idempotent by durable outbox ID plus Entry/version (and call fingerprint when added); an indexing failure retries that outbox, never Entry creation. Do not add a second indexing outbox path.
- If current Entry creation performs nontransactional external work inside the transaction, split it into an idempotent outbox before enabling the golden path.
- Update/delete/relation creation remain denied even if their underlying services are technically callable.

The local atomic transaction first locks/verifies Run/call revisions, then performs validation/flushes, then writes the inline result and atomically sets Attempt `committed`, call `succeeded`, and `side_effect_started_at=database_now`. Injecting failure before/after each flush or before commit rolls back all rows. If commit succeeds but the response is lost, recovery reads the succeeded call/result/Entry by `source_capability_call_id` and never dispatches the core again.

## External Write and Uncertainty Contract

No external write is enabled for normal users in this plan, but the ledger contract and tests must be complete before later enablement.

### `external_idempotent`

- Persist `executing`, Attempt, key, and `side_effect_started_at` before network send.
- Send exactly the same provider-supported key on every allowed retry.
- Retry only errors explicitly classified by transport/provider contract; bound attempts/backoff/deadline.
- A success response must echo or otherwise prove the request identity before marking success.

### `external_reconcilable`

- After timeout/disconnect/ambiguous 5xx, commit `unknown` immediately.
- Use the provider’s read-only status lookup before any retry.
- Mark success/failure from verified provider evidence, or stop in `needs_reconciliation`.

### `non_retriable`

- Persist `side_effect_started_at` before send.
- Any outcome that cannot prove “not accepted” or “succeeded” becomes `needs_reconciliation`.
- Automatic retry, alternative target, or model-driven compensation is forbidden.

Cancellation prevents a not-yet-started effect. Once a remote request may have started, cancellation records user intent but cannot claim rollback; the call must reach a proven terminal/reconciliation state.

### Ledger activation sequence
